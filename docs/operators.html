From typed observations to replayable findings

Reasoning operators and verifiers

CircuitJS describes a method without embedding arbitrary executable code. Operators provide the approved algorithms behind that method; verifiers independently check the witness required to publish a finding. The scheduler connects both while preserving types, provenance, budgets, and failure states.

Why circuits call a registry

Different rules need genuinely different algorithms. Phrase linting needs exact source scanning. Continuity needs ordered events and state transitions. Normative deadlines need temporal calculation and explicit exception policy. Technical consistency may need unit conversion or constraint comparison. Flattening all of these into a single generic “reason” operation would hide the real semantics and make independent verification impossible.

A circuit therefore refers to an exact versioned operator identifier. The trusted registry binds that identifier to an implementation contract: input and output shapes, determinism, effects, capabilities, resource limits, cost, sandbox policy, and witness requirements. Static compilation fails when an operator or verifier is absent, unknown, or not permitted by the release.

flowchart TB
  PORT[Typed observations] --> OP[Registered operator]
  OP --> VER{Candidate witness verified?}
  VER -->|accept| PUB[Publish bounded finding]
  VER -->|reject| DIAG[Reject + diagnostic]

The solver is not its own judge. An operator can be complex, but publication depends on a verifier checking concrete properties of its witness. Rejection remains evidence and never becomes a finding.

How the scheduler executes a circuit

  1. Bind external ports. The runtime selects LongTextJS observations by nominal type and version, accepted epistemic statuses, scope, and cardinality. It propagates the weakest premise guarantee.
  2. Build a dependency plan. Node references form a directed graph. Filters can move ahead of expensive joins only when equivalence is preserved. Ready pure nodes may run concurrently without changing deterministic output order.
  3. Resolve every executable node. Relational and control primitives use built-in semantics; call, state, temporal, search, judge, and verification nodes resolve exact registry entries and declared capabilities.
  4. Execute with immutable values. Nodes receive plain-data inputs and return plain-data outputs with provenance. A node cannot mutate LongTextJS, release data, or another node’s result.
  5. Route controlled outcomes. Empty results, not-applicable conditions, budget exhaustion, operator faults, and verifier rejection follow declared routes rather than becoming thrown-away logs.
  6. Persist the trace. The run records the plan, resolved versions, node inputs and outputs, budgets, witnesses, verifier decisions, and findings needed for replay and review.

A witness makes a result contestable

A verdict such as “deadline missed” is too compressed to verify. Its witness must carry the trigger observation, rule identity and version, relevant calendar or elapsed-time policy, outage intervals, computed deadline, candidate actions, evidence coverage, and selected verdict. The temporal verifier recomputes those pieces instead of trusting the operator’s boolean.

The same principle applies to simpler cases. A lexical witness contains the rule, exact anchor, and matched span. A continuity witness contains the two material events, object identity, intervening event domain, transition policy, and state gap. A shortest-path witness contains the graph, path, cost, and any potential or optimality information needed by the checker.

Verifier output is not just accepted or rejected. It records the verifier identifier, checked properties, diagnostics, source dependencies, and guarantee obtained. This allows the report to say what was certified rather than displaying a generic “verified” badge.

Verification does not erase uncertain premises

A verifier certifies only the property it replayed. If a semantic translator proposed that a sentence describes a retrieval event, deterministic state replay can certify the state calculation given that event; it cannot retroactively make the event classification mechanical. The finding’s guarantee is bounded by the weakest material premise and the verifier’s own contract.

Completeness-sensitive operations

Anti-joins and “no event found” conclusions require a coverage token whose domain exactly matches the collection being excluded. The continuity verifier inspects all materialized intervening object events rather than trusting a candidate to list only convenient ones. Lexical completeness scans every qualifying block, not only retrieved passages. If the document source or extraction profile cannot establish the required domain, the circuit must return incomplete or undetermined.

Dynamic observation requests

An operator may discover a bounded semantic question that static planning could not specialize, such as “find every retrieval, transfer, or replacement event for this phone between scenes 4 and 12, including negated and hypothetical mentions.” It returns a typed NeedObservation, not a free-form model prompt. The analyzer materializes the request through the normal translation and anchoring path, then reruns the dependent portion of the circuit. Dynamic rounds and model calls consume explicit budgets and remain visible in the trace.

Budgets, caching, and isolation

The scheduler enforces run, circuit, node, dynamic-demand, wall-time, memory, model-call, and operator-specific bounds. Search-style operators additionally bound expanded states and frontier size; fixpoint execution requires a finite domain and deduplication. Exhaustion may preserve a diagnostic candidate but cannot publish it as a verified result.

Deterministic node cache keys include the circuit and node versions, operator implementation, resolved inputs, the complete LongTextJS semantic program, and operational context. Including the full program matters because an operator or verifier may consult anchors, task policy, or coverage outside its immediate row array. Model calls are captured; they are reused deterministically only through an explicit replay capture.

Pure operators can run in process. Model, network, solver, native, or otherwise effectful operators require controlled adapters and may be placed in worker threads or child processes. A circuit receives only declared capabilities, never ambient filesystem or network access.

Add an operator without expanding hidden trust

  1. Write down the semantic role, stable versioned input and output data, determinism, effects, limits, and failure modes.
  2. Design the witness before the solver implementation. The witness should be smaller and easier to check than reproducing the whole search procedure.
  3. Implement the operator outside agent-editable CircuitJS and register it under an exact identifier.
  4. Implement an independent verifier or explicitly bound the result as model judgment. Test that corrupted witnesses are rejected.
  5. Add unit tests for normal, boundary, invalid, adversarial, and exhausted cases, including provenance and deterministic ordering.
  6. Add natural benchmark cases showing that real document observations reach the operator with the intended semantics.
  7. Update the relevant DS, registry documentation, security capabilities, and candidate release. Registration alone does not qualify a domain use.
