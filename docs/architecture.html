The system in one page

Two programs, two CNL outputs, one learning loop

LongTextJS represents the concrete input; CircuitJS represents reusable rule knowledge. Validation turns a document into a CNL audit. Planning turns an idea into a CNL generation specification. Learning builds candidates for both; maintainers publish them explicitly.

flowchart TB
  INPUT[Document or idea] --> LTX[LongTextJS]
  CIR[Published CircuitJS release] --> GRAPHS[Validation or planning graph]
  LTX --> GRAPHS --> CNL[CNL audit or generation plan]
  CNL -. optional plan realization returns as input .-> INPUT

The runtime architecture. The graph purpose selects the CNL output profile. The two graphs share authority, schemas, operators, compatibility, provenance, and release identity, while retaining different control flow.

Architecture of one verification

A document is snapshotted, compiled into LongTextJS, checked against CircuitJS observation contracts, executed, verified, and persisted as CNLAuditReport. The question is: what can this release responsibly say about this document?

Architecture of CNL generation planning

An idea becomes LongTextJS, planning circuits apply the released theory, and CNLGenerationPlan becomes the primary specification. A rule-to-plan witness proves where each applied rule shaped it. A model may optionally realize it; validation then audits the candidate.

Architecture of learning

Authority, examples, feedback, and issues enter an isolated authoring job. The job produces candidate schemas, producers, circuits, and benchmarks. A maintainer later chooses whether to publish that candidate. The important question is: what must change before future runs may judge more or judge differently?

The three boundaries that make it work

BoundaryWhat stays on each sideFailure prevented
Source / judgmentLongTextJS records anchored observations; CircuitJS derives rule-dependent conclusions.An interpretation is not presented as source, and extraction does not decide the verdict it is meant to support.
Candidate / publicationOperators may propose results; registered verifiers and finding contracts control emission.A plausible candidate is not presented as a verified finding.
Learning / productionLearning edits staged candidates; production reads an immutable published release.A production document or reviewer comment cannot rewrite the rule during the run.

The connector is a contract, not a shared giant ontology

Circuit compilation walks backward from every output and derives the LongTextJS types that can influence it. Pre-publication checks require each critical type to have an approved producer. During a run, compatibility proves that this particular source produced acceptable observations and coverage. These are different checks: a release may know how to produce narrative.object-event@1 in general and still fail to produce enough such events for one damaged or unfamiliar document.

The detailed mechanism is in The observation contract. This is the central link between the two halves of the documentation.

Implementation shape

The current product is a modular local Node.js application, not a required microservice deployment. src/runtime/production-run.mjs owns direct validation, src/generation/runner.mjs owns planning and the optional realization branch, src/runtime/analyzer.mjs supplies the shared validation path, src/learning/runner.mjs owns isolated authoring, and src/release/manager.mjs owns explicit publication and active-pointer replacement.

Architecture versus extension surface. The runtime supports versioned schemas and registered reasoning operators, but the repository does not ship a published implementation for every literary, legal, scientific, multimodal, or solver-backed theory described by the broader design. Missing domain capability remains a compatibility gap.
