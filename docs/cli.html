CLI and agent workspaces

The CLI looks file-oriented—select an agent, supply Markdown, receive a report—but every command acts on a persistent, versioned workspace. Understanding that workspace is the key to running, debugging, teaching, and upgrading a linter safely.

Start with the executable example

The repository’s editorial-demo agent already has the published MVP release 0.1.0 active. Run its benchmark before analyzing a document so you see both halves of the operational contract:

node bin/nllagent.mjs benchmark --agent editorial-demo

node bin/nllagent.mjs run \
  --agent editorial-demo \
  --input data/editorial-demo/benchmark/public/weak-phrase/input.md \
  --output /tmp/editorial-report.md

The benchmark command tests the selected release against its natural cases. The run command copies the input into a new run directory, resolves the release, compiles LongTextJS, executes compatible circuits, verifies candidates, and writes /tmp/editorial-report.md. The command result also contains the run identifier. Use that identifier to inspect persisted evidence or attach reviewer feedback.

flowchart TB
  CMD[run command] --> SNAP[Source + release snapshot]
  SNAP --> ANALYZE[Compile + gate + execute]
  ANALYZE --> AUDIT[CNLAuditReport]
  AUDIT --> DELIVERY[Run artifacts + Markdown view + exit code]

The CLI starts a transaction, not a chat. The report is one rendering of a complete run record. Even a stopped run preserves enough evidence to explain why no verdict was published.

A named agent is the isolation boundary

Every command that changes or executes domain behavior names an agent. An agent is not an LLM session. It is a persistent linter project with its own authority, extraction profiles, circuits, benchmark suites, candidates, release lineage, runs, issues, and feedback.

node bin/nllagent.mjs agent init \
  --agent editorial \
  --description "Editorial review for English prose" \
  --language en

node bin/nllagent.mjs agent list
node bin/nllagent.mjs agent inspect --agent editorial --json

Names are path-safe workspace identifiers. The default persistent root is ./data; --data-root /controlled/location moves the entire agent collection for one command. Avoid pointing different operational environments at the same writable root unless their locking and release policy are coordinated.

flowchart TB
  ROOT[data/] --> A1[editorial agent]
  ROOT --> A2[compliance agent]
  A1 --> W1[Own circuits + benchmarks]
  A2 --> W2[Own circuits + benchmarks]

Shared engine, separate theories. Several agents use the same CLI and trusted registries, while every agent owns an independent authoring, release, benchmark, and run history.

Run a document

nllagent run \
  --agent <name> \
  --input <document.md> \
  --output <report.md> \
  [--release <version>] \
  [--translator auto|achilles|codex|none]

Without --release, the command uses the agent’s active release. Selecting a version explicitly is useful for comparison and replay, but it still must be a published release. Input is currently Markdown; the copied source and its digest become the lexical authority of the run. The output file is written for both successful and controlled stopped outcomes.

The command rejects unknown flags, conflicting translation switches, surplus positional arguments, unsafe agent names, missing input, and missing or unpublished releases before treating the invocation as a valid production run. Once a run exists, runtime diagnostics are persisted alongside its partial artifacts.

Compile an idea into a CNL generation specification

nllagent plan \
  --agent <name> \
  --input <idea.md> \
  --output <plan.cnl.md> \
  [--release <version>] \
  [--translator auto|achilles|codex|none]

The command compiles the idea through LongTextJS and the release’s primary planning circuit. Its primary output is the CNL specification; deterministic planning works with --translator none. CNL contains the concrete document design, content sequence, and verified rule-to-plan locations, not a list of rule constraints.

To ask nllAgent to realize and validate the plan, add:

  --realize-output <draft.md> \
  [--max-revisions <0..10>] \
  --translator auto

--max-revisions is rejected without --realize-output. Realization uses a schema-bound backend, then sends every candidate through CNL audit mode. Read CNL specification mode for circuit reuse and artifact details.

Choose semantic translation deliberately

nllagent model inspect --json
nllagent run ... --translator auto
nllagent run ... --translator achilles
nllagent run ... --translator codex
nllagent run ... --translator none
# --no-llm is an alias for --translator none
SelectionBehaviorWhen to use it
autoPrefers configured AchillesAgentLib; otherwise uses the shipped reference Coding Agent translation adapter.Normal operation when semantic observations may be required.
achillesRequires a resolvable and configured AchillesAgentLib LLMAgent; translation-class work prefers Spark when exposed.Environments that evaluate and operate an Achilles model profile.
codexSelects the current OpenAI Codex reference implementation of the generic Coding Agent backend.Explicit fallback testing or installations intentionally using that adapter.
noneDisables semantic calls. Deterministic structural and lexical rules still run; missing semantic requirements become compatibility gaps.Offline deterministic agents, diagnostics, or fail-closed operation without a model.

The option name codex, --codex-bin, and NLL_CODEX_BIN are current compatibility surfaces, not a claim that the architecture requires Codex. A future Coding Agent adapter can preserve the same schema, workspace, capture, and capability contract with a different process protocol. See Semantic translation for that boundary.

Read the result at two levels

The requested Markdown file is the reviewer view of canonical cnl-audit.json: status, release, coverage limits, findings, evidence, and remediation. The run directory contains the source package, canonical LongTextJS, compatibility and coverage reports, circuit plan, execution trace, findings, conflicts, verifier results, model captures, CNL audit, and rendered report. A Coding Agent translation fallback additionally creates small translation/call-NNNN/ folders with request, schema, result, events, and diagnostics.

Start with the report. If a finding is disputed, inspect its anchor and verifier record. If no finding was produced, inspect compatibility and coverage before looking at circuit execution. If semantic extraction failed, inspect model captures and the individual translation call. Artifacts and statuses provides this debugging path in detail.

Benchmark and publish manually

nllagent benchmark --agent editorial
nllagent benchmark --agent editorial --release 1.0.0 --json

nllagent release publish --agent editorial --candidate 0.1.0

benchmark runs the active or selected release against the agent’s declared natural suites. release publish is the explicit maintainer action: it validates the candidate manifest, circuit grammar, registry links, observation contracts, producer alignment, benchmark snapshot, and candidate immutability; creates the closed release; validates it again; and atomically updates the active pointer. Learning never invokes this command.

Open a controlled learning job

nllagent learn \
  --agent editorial \
  --rules ./rulebook

This asks the configured Coding Agent adapter to build or repair agent-local authoring artifacts in staging. The audited result may produce a candidate, but it cannot publish or activate one. The current executable override is --codex-bin <path> because OpenAI Codex is the shipped reference adapter; this vendor detail is confined to that adapter.

Learning is appropriate when rules, examples, or issues should change the reusable theory. It is not a recovery flag for a production run. A blocked document remains blocked under its original release; after a maintainer reviews and manually publishes a new candidate, the operator may run the document again as a new run. See Learning workflow.

Record evidence, not hidden exceptions

nllagent issue list --agent editorial
nllagent issue list --agent editorial --status open --json

nllagent feedback add \
  --agent editorial \
  --run <run-id> \
  --type observation-correction \
  --message "The speaker in paragraph 12 is Alice."

Issues are runtime-generated statements about compatibility, materialization, verification, benchmark, or execution failure. Feedback is reviewer evidence attached to a run. Neither automatically changes a rule. A later learning job snapshots authorized records and converts useful examples into candidate changes and regression cases.

A practical troubleshooting order

  1. Run agent inspect and confirm the intended agent and active release.
  2. Run model inspect --json if semantic observations are expected.
  3. Read the report’s terminal status, active circuits, and declared limits.
  4. For stopped runs, inspect compatibility and coverage before circuit traces.
  5. For rejected candidates, inspect verifier results and witness data.
  6. For changed behavior after an upgrade, compare explicit release versions and the publication semantic diff.
  7. Record a scoped issue or feedback item when the discrepancy should inform learning.
