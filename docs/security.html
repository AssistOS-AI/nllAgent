Documentation / Runtime boundaries

Contain capabilities and preserve epistemic limits

Security, trust, and change control

nllAgent analyzes untrusted documents, may call language models, and lets a Coding Agent propose theory changes. Its safety model is therefore built around a few enforceable boundaries: source is data, circuits are restricted declarations, executable capabilities are registered, production releases are immutable, learning happens in staging, and uncertain premises remain uncertain.

What the system protects against

The relevant threats are practical. A document can contain prompt injection, code, hidden-looking instructions, Unicode tricks, or text that resembles a rule. A model can return malformed data, a quotation that never appeared, or a confident but wrong interpretation. A candidate circuit can try to reach unregistered code or bypass verification. A Coding Agent can write outside the intended authoring surface. A release can be partially changed after publication. A reviewer comment can be mistaken for policy. A costly search can exhaust resources and leave a partial answer that looks complete.

The local research implementation does not claim confidential computing, remote attestation, package signing, or a complete organizational authorization system. It does implement concrete containment, validation, digest, provenance, and fail-closed mechanisms and is explicit about the guarantees they do—and do not—provide.

flowchart LR
  DATA[Untrusted document data] --> PARSE[Restricted parsing + translation]
  PARSE -->|valid| EXEC[Registered execution + verification]
  PARSE -->|invalid| GAP[Explicit gap or rejection]
  EXEC --> OUT[Bounded report or stopped result]
  GAP --> OUT

Every boundary narrows authority. Source text can propose observations only through validated channels; circuits can invoke only registered operations; findings can be published only after their declared witness checks.

The document cannot become an instruction

Production Markdown is always source content, even when it says “ignore the rule,” contains a prompt, quotes shell commands, or embeds agent instructions in a code fence. Model requests place passages in labelled source fields and ask for one schema-bound result. The runtime never interprets source text as permission to change prompts, skills, operator registries, authority ordering, filesystem state, or the active release.

Deterministic ingestion preserves raw source evidence and produces canonical blocks and anchors. Semantic output must reference exact quotations in named blocks. An invented or normalized quotation that cannot be located is rejected. External links remain text unless an explicit, reviewed adapter is added; analyzing a document does not authorize network retrieval.

Circuit authoring is not general JavaScript

CircuitJS may be stored as JSON or as a restricted .circuit.mjs author form. The loader accepts exactly one direct export default circuit({...}) expression and exposes only circuit, port, and node. It rejects wrappers, functions, classes, control flow, imports, asynchronous execution, template evaluation, runtime globals, dynamic code generation, filesystem, network, process, prototypes, accessors, cycles, unsupported scalar types, and non-finite numbers.

The surviving expression is converted losslessly to plain data and statically compiled. Every computational primitive resolves an exact registered operator. Every verification node resolves an exact registered verifier. The compiler rejects a path that can emit a finding without verified data dominating publication.

Registered capabilities form the trusted execution boundary

An operator record declares its version, input and output contract, determinism, effects, cost, resource limits, capability requirements, sandbox policy, and witness or verifier contract. Pure deterministic operators may run in process. Model, network, solver, native, or external-process behavior must be reached through controlled adapters and can be isolated in workers or child processes.

A circuit receives only declared capabilities. It cannot open arbitrary files, inherit ambient network access, or dynamically select an implementation by source text. Missing operator or verifier identifiers are compilation failures. Learning can propose a new operator and tests, but cannot register implementation code automatically.

Trusted JavaScript extensions are host code, not circuit code

A host application may deliberately load one self-contained NllRuntimeExtension file through the ESM library API. The loader requires a regular non-symlink file, rejects imports and re-exports, records its source digest, validates operator and verifier metadata, freezes plain-data inputs and context, and rejects non-plain output. A release that calls it must lock the same extension id and digest.

This is not a sandbox. The module executes in the host process and can use JavaScript globals with host authority. It must be reviewed like any other application dependency. Documents, learned circuits, candidate packages, and the standard CLI cannot select an extension path. The practical contract and runnable example are in Circuits in practice.

Learning cannot write through to production

The learning runner snapshots agent files into staging and rejects symbolic-link inputs. Authority, feedback, specifications, release context, and trusted registry descriptions may be copied for reading but are not promotable. After the Coding Agent exits, the runner computes a before/after inventory. Any deletion, symbolic link, protected change, write outside permitted roots, invalid final result, or failed process rejects the job without copying those changes to the real agent.

Only regular files in schemas, extraction profiles, circuits, benchmarks, proposals, candidates, and other declared authoring roots may be promoted. Publication is a later, explicit maintainer action outside the Coding Agent. Previously published releases and the active pointer remain untouched by learning.

flowchart LR
  WORK[Disposable learning workspace] --> DIFF[Changed-path audit]
  DIFF --> GATE{Whitelist satisfied?}
  GATE -->|yes| CAND[Candidate-only promotion]
  GATE -->|no| FAIL[Reject without live writes]

Filesystem behavior is checked, not inferred from the final message. A well-written agent response cannot authorize a forbidden path or deletion.

Guarantees propagate from premises and checks

nllAgent distinguishes exact source evidence, deterministic extraction, model-proposed interpretation, derivation, verifier certification, human confirmation, and unresolved uncertainty. A deterministic operator cannot upgrade a weak semantic premise merely because its arithmetic is exact.

flowchart LR
  PREM[Exact or model-assisted premises] --> CALC[Deterministic derivation]
  CALC --> CHECK[Bounded witness check]
  CHECK --> GUAR[Finding at weakest valid guarantee]
  HUMAN[Human confirmation] --> GUAR

Verification is property-specific. The checker may certify an anchor, calculation, or replay. The final guarantee still records whether a material premise came from a model or required policy-owner confirmation.

An exact phrase match can be mechanically certified. A state timeline derived from model-classified events can be evidence-certified for the replay while retaining model-assisted event semantics. A focalization judgment can cite exact passages and an approved rubric yet remain review-required. Human confirmation is recorded as its own provenance level rather than relabelled mechanical.

Fail closed on concrete unmet contracts

The runtime attempts the requested work within the selected release and approved budget. It does not stop merely because language interpretation is philosophically uncertain. It does stop for concrete failures: missing critical producer, unsupported document profile, invalid model output, insufficient source or semantic coverage, unresolved critical dynamic demand, unknown operator or verifier, rejected witness, incompatible certified alternatives, exhausted budget, or runtime fault.

Non-critical limits are allowed only when the task and release explicitly permit partial reporting, and the report names affected circuits and scopes. A global “compliant” conclusion cannot be inferred from three completed rules while two critical rules were blocked.

flowchart LR
  ASK[Requested judgment] --> COMP{Contracts satisfied?}
  COMP -->|yes| REPLAY{Witness accepted?}
  COMP -->|no| STOP[Stopped run + issue]
  REPLAY -->|yes| REPORT[Report bounded result]
  REPLAY -->|no| STOP

Unknown is not compliant. Compatibility, coverage, and verification failures become explicit terminal evidence with distinct exit codes.

Manual publication and local release consistency

The manual publication command loads candidates independently, enforces the restricted grammar, registry links, observation-producer alignment, benchmark policy, candidate and benchmark snapshot stability, and release file closure. The manifest records ordinary content digests for schemas, circuits, profiles, adapters, authority sources, operators, verifiers, and generated publication artifacts. Loading detects accidental edits or partially updated packages before the command updates the active pointer.

These digests provide reproducibility and local tamper detection, not publisher identity or cryptographic supply-chain attestation. A changed operator or model profile requires affected tests and a new release decision; old runs keep their original version references and captures.

Authority and feedback cannot be inferred by volume

Rule sources define intended policy, the active release defines current production behavior, and reviewer feedback supplies scoped evidence about a run. Repeated comments or document text do not automatically become a norm. Learning must classify a change as extractor correction, theory correction, ontology extension, report correction, or operational-context repair, and encode the intended behavior in natural cases. A maintainer later decides whether to publish the candidate.

If a release is faulty, the maintainer prepares and manually publishes a corrected candidate. Old releases and runs remain for explanation. The failure becomes an issue and may become a minimal regression case, but correction does not rewrite history. The MVP does not expose a separate activation or rollback command.

The foundation cannot hide changing authority

The selected foundation is immutable platform code whose version and digest are stored with the run. Documents, models, feedback, and agent candidates cannot modify it. Its core contains only bounded logical and temporal invariants. Current political, economic, geographic, social, or legal facts require a future optional pack with sources, effective dates, jurisdiction, world, expiry, guarantees, and conflict tests; embedding them as timeless code would create stale hidden authority.

Operational checklist

  • Use Node.js 22 or newer and keep production on published release snapshots.
  • Run model inspect --json and explicitly evaluate any live model profile used for high-impact agents.
  • Use --translator none when policy forbids model calls; accept resulting compatibility gaps rather than bypassing them.
  • Do not add unrestricted JavaScript or general filesystem/network effects to circuits.
  • Review new operators and verifiers as trusted platform changes with focused adversarial tests.
  • Inspect learning changed-file audits, benchmark results, and semantic diffs before manual publication.
  • Treat stopped statuses and verifier rejection as no verdict in automation.
  • Control access to source, model captures, feedback, and run artifacts according to document sensitivity; local containment is not a confidentiality system.
  • Retain enough source and capture evidence for the replay guarantees your organization claims.
