Runtime, SSA, and semantic transactions

This page follows one value from a ready node to a committed semantic result.

  1. The planner selects a circuit chain that can provide the requested capability.
  2. A rule binding or stage instance becomes READY after its inputs exist.
  3. The node runs against a stable store snapshot and buffers derivations or outputs.
  4. Runtime validation checks term types, provenance, destination layer, duplicates, and invariants.
  5. Commit publishes immutable values and activates dependants; failure discards the entire buffer.

The SSA boundary

Published values have one producer. Local variables do not: a graph solver can update its own arrays and maps. The stage publishes one final term set or output, so SSA describes semantic dataflow instead of JavaScript syntax.

Dynamic graph growth

Rules can create work for each binding; stages can request capabilities or subcircuits. Growth is append-only inside a snapshot. A canonical template–binding–context instance is created once. Resource exhaustion produces a blocked result.

Current implementation boundary

Sequential hierarchical scheduling, typed matching, async stages, transactions, subcircuits, and lifecycle trace are implemented. Parallel merge, persistent node cache, epochs, and generalized expansion remain planned runtime work and are not presented as current guarantees.
