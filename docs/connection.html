The typed joint between document and theory

How LongTextJS and CircuitJS actually connect

They do not connect because two fields happen to share a name. A compiled CircuitJS graph publishes an observation contract. Manual publication checks that approved LongTextJS producers can satisfy it. A production run checks that this document satisfied it now.

flowchart LR
  THEORY[CircuitJS graph] --> CONTRACT[Derived observation contract]
  PRODUCERS[LongTextJS producers] --> GATE{Alignment + run compatibility}
  CONTRACT --> GATE
  GATE --> RESULT[Ready circuit or precise blocked gap]

One contract, two checks. Release alignment establishes a valid production path in general. Run compatibility establishes that the concrete source, observations, statuses, resources, and coverage satisfy that path.

Foundation circuits use the same joint. In core mode, the platform materializer contributes its own typed observations and capabilities, and the analyzer runs ordinary binding–operator–verifier circuits before the agent release. Their open-world token proves only the documented pattern scan, not exhaustive semantic knowledge. In off mode the overlay is absent by explicit selection.

What the contract contains

For each external observation binding that can affect an output, the contract records the nominal types, version, cardinality, accepted epistemic statuses, required coverage, criticality, scope relation, and guarantee requirements. A binding may also contain safe local field matchers. The persisted version-1 contract retains the historical ports key for compatibility; it describes bindings, not network sockets. The default logical-consistency circuit compiles to this contract:

{
  "kind": "ObservationContract",
  "schemaVersion": 1,
  "circuit": "foundation.logical-consistency@1.0.0",
  "ports": [{
    "name": "assertions",
    "types": ["foundation.state-assertion@1"],
    "cardinality": "many",
    "statuses": ["extracted"],
    "coverage": "open-world",
    "critical": true,
    "scopeRelation": null,
    "guarantee": null
  }]
}

Experimental QueryContract extension

DS020 keeps this ObservationContract and derives a QueryContract for work beyond local binding matchers: joins, projected fields, total order, exact absence coverage, and conservative row/intermediate budgets. It is additive; generated observation bindings remain the compatibility boundary used by the ordinary graph.

The important difference is coverage precision. The implemented antiJoin cannot accept a token merely because it mentions the same nominal type: source revision, scope, channels, type, producer/method, exclusions, completeness mode, verification, an empty failure set, and producer status capability must match exactly. Broader subsumption, correlated notExists, domain-specific failure matching, and world-aware signatures remain future work. See the closed-world and unknown executions.

The ordinary contract says more than “the circuit reads states.” It accepts only extracted foundation assertions and treats the binding as critical, while its open-world coverage prevents the circuit from claiming that every implicit state in the document was discovered. A query-authored domain rule can add exact fields, order, and coverage obligations through its QueryContract without weakening this binding contract.

The connection is checked at four moments

  1. Circuit compilation derives actual demand. src/circuit/compiler.mjs walks backward from declared outputs through emit, verify, calls, joins, and derivations. Only external bindings that can influence the result enter the contract. A circuit cannot hide an undeclared premise on a dead side path.
  2. Manual publication links producers. src/release/manager.mjs builds a producer-consumer matrix. Built-in Markdown structure, published extraction profiles, and approved adapters are compared with each critical binding’s type, statuses, coverage, and guarantee. A critical binding without a compatible producer rejects the candidate.
  3. Production checks materialization. src/runtime/compatibility.mjs evaluates the actual LongTextJS program. It checks observations, cardinality, statuses, capabilities, gaps, channels, structures, coverage, operational resources, and profile limits. A declared producer cannot manufacture evidence that this document did not yield.
  4. Execution verifies a witness. A ready circuit may compute candidates, but its finding contract still controls publication. The registered verifier checks the precise witness against source and released policy. Compatibility answers “may this theory run?”; verification answers “does this candidate support this claim?”

Worked example: two incompatible door states

The Quick Tutorial example makes the complete joint visible:

  1. The Markdown compiler creates exact sentence observations and anchors for “The north door is open at noon” and “The north door is not open at noon.”
  2. The selected foundation materializer creates two extracted foundation.state-assertion@1 observations, with opposite polarity but the same normalized subject, state, time, frame, and source world.
  3. The circuit observation binding asks for exactly that type and status. Compatibility confirms the producer capability and its explicit open-world pattern-scan coverage.
  4. The state-conflict operator compares the bounded contexts and constructs a candidate containing both observation identities and anchors.
  5. The independent verifier rereads the observations, source revision, exact anchors, context, and polarity. Only its accepted candidate becomes the CNL warning shown in the tutorial.

What changes for semantic observations

Suppose a continuity circuit consumes narrative.object-event@1. Its published extraction profile may produce proposed leave, retrieve, transfer, and use events. Pre-publication checks can prove that a producer exists and that natural benchmark cases give the type operational meaning. Production can prove that candidate events were anchored and that the required scope was processed. A state verifier can replay the published transition policy.

None of those steps turns model interpretation into mechanical fact. The final guarantee is bounded by the event status, identity evidence, and coverage. If the phone identity is ambiguous or the intervening chapters were not materially covered, the correct result is ambiguous or incomplete. This is why the connector includes status and coverage rather than just a JSON schema.

Why this architecture works

The document compiler is guided without being told which verdict to produce. The theory is reusable without pretending to understand every source. Static linking catches impossible packages before release. Runtime compatibility catches concrete documents outside the calibrated domain. Witness verification catches bad candidates after execution. Each failure lands at a named boundary that can later become a targeted learning task.

The same joint supports both CNL profiles. Planning circuits demand structural or semantic observations from the idea and emit an idea-specific CNL specification with verified rule-to-plan coverage. Validation circuits demand observations from an existing or realized document and emit findings assembled into a CNL audit. Neither output copies the rulebook or bypasses its observation contract.
