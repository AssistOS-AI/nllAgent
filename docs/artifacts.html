Persistent identity, provenance, and run results

nllAgent stores two canonical CNL products. A validation run owns CNLAuditReport; a planning transaction owns CNLGenerationPlan. Markdown files are human-readable views, while the structured artifacts preserve reproducibility and contestability.

Four identities prevent silent history changes

IdentityLifetimeWhat remains fixed
NaturalLanguageLinterProject / named nllAgentLong-livedIntended use, authority, agent-local authoring and benchmark lineage, release history, and operational policy.
CandidateUntil published or rejectedA proposed package version assembled from the current authoring surface.
NaturalLanguageLinterReleaseImmutable after publicationThe exact schemas, profiles, circuits, compatibility declarations, benchmark snapshot and results, verifier/operator references, and digests published together.
NaturalLanguageLinterRunImmutable historical executionInput source, task, release, backend selection, accepted captures, trace, findings, limits, issues, and terminal status.

A new release does not rewrite an old run. Rerunning the same document under a newer theory creates a second run that can be compared with the first. This is what makes policy changes, extractor repairs, and new capabilities auditable rather than retroactive.

flowchart LR
  AGENT[Named agent] --> REL[Published release]
  REL --> RUN[Document run]
  RUN --> EVID[Findings + reviewer feedback]
  RUN --> ISSUE[Issues + learning needs]

Lineage flows forward. Evidence from a run may motivate a later candidate, but it never edits the release or run that produced it.

Inside a production run directory

A successful or controlled stopped invocation creates data/<agent>/runs/<run-id>/. The precise set can grow as optional features are used, but the core artifacts have stable roles:

ArtifactQuestion it answers

input.mdWhat exact UTF-8 Markdown did the runtime analyze?
source-package.jsonHow was the source divided into canonical blocks and addressed?

longtext.jsonWhich observations, views, identities, capabilities, coverage statements, gaps, and task entered analysis?
compatibility.jsonWhich circuit and port obligations were satisfied, limited, or blocked, and by which producer evidence?
coverage.jsonWhich source, scope, type, and method domains were inspected, and which gaps remain?
circuit-plan.jsonWhich circuits were active or blocked, and how were their nodes scheduled?
semantic-trace.jsonWhich typed node inputs, outputs, dependencies, and dynamic observation requests produced the result?
findings.jsonWhich structured findings passed publication requirements?

The requested --output file is a copy of report.md, a deterministic view of cnl-audit.json. The JSON is the canonical audit product; the external Markdown path is a delivery convenience.

Inside a CNL planning transaction

data/<agent>/planning-runs/<id>/ stores planning.json, the original idea.md, its LongTextJS program, canonical CNL/Plan-1 in cnl-plan.json, rendered plan.cnl.md, planning compatibility and trace files, and any semantic-observation model captures. The plan contains its mechanically checked rule-to-plan witness. Optional realization adds realization/document.md, realization captures, and realization/attempts/attempt-NN/ directories with complete nested CNL audit evidence.

The external plan and optional document paths are delivery copies; the planning directory is the lineage. The final record identifies the plan and, when relevant, which realization attempt succeeded or why the last candidate needs review. See the worked artifact tree.

Anatomy of a finding

A finding is not just a message and location. It retains the rule identity and normative basis, verdict and severity, primary and supporting anchors, premise provenance, witness, verifier decision, guarantee, explanation envelope, remediation, limitations, circuit and release identity, and run scope. Those fields allow several different disputes:

  • “The quotation is not the passage the rule should inspect” contests the anchor or view.
  • “Those two mentions are different phones” contests identity.
  • “Dialogue is exempt” contests circuit scope or exception priority.
  • “The supplied log was incomplete” contests coverage.
  • “This policy source has lower authority” contests the theory or operational context.
  • “The explanation says more than the witness proves” contests rendering or guarantee propagation.

Feedback records the object being contested, rather than appending an unstructured exception to the active release.

Terminal statuses are valid outputs

StatusMeaningCLI exit
reportedAll declared preconditions for the active findings were satisfied. Findings can still make the policy result blocking.0, or 2 for blocking findings
reported-with-limitsThe reported circuits and scopes completed, with explicit non-critical compatibility or materialization limits.0, or 2 for blocking findings
stopped-incompatibleA critical language, format, ontology, producer, source, or operational-context obligation is missing.3
stopped-incompleteRequired dynamic materialization or coverage could not be completed.4
stopped-budgetThe approved run, model, dynamic-round, operator, or wall-time budget ended before the required analysis completed.5
review-required-conflictVerified alternatives are incompatible and the release has no authorized rule to collapse them.6

Only reported and explicitly scoped reported-with-limits are reports of completed work. None of the stopped states means “no violation.” In CI, keep their exit codes distinct from blocking findings so missing knowledge is not mislabeled as compliance.

What manual publication freezes

A published release under data/<agent>/releases/<version>/ is a closed file set. Its manifest names and digests all shipped files; undeclared additions or modified bytes make loading fail. Depending on the candidate, the snapshot includes circuits, schemas, extraction profiles, compatibility declarations, authority mappings, benchmark cases and results, derived observation contracts, alignment report, semantic diff, impact map, publication record, and release manifest.

release publish is an explicit maintainer action. It checks the candidate, builds the closed snapshot, loads that snapshot again, and then atomically updates the active pointer. Ordinary production resolves the pointer once at run start and does not switch releases mid-execution.

flowchart LR
  SNAP[Candidate + benchmark snapshot] --> TEST[Manual publication checks]
  TEST -->|pass| PACK[Closed release file set]
  TEST -->|fail| REVISE[Candidate revision]
  PACK --> PROD[Atomic active pointer update]

Publication freezes and selects. The tested candidate bytes and natural cases travel together into the release, and the same manual command selects that published version for future runs.

Issues and feedback are different evidence

An issue is generated by the runtime when a contract or mechanism fails: incompatibility, incomplete coverage, verifier rejection, benchmark mismatch, operator error, or unexpected runtime failure. It records reproduction context, affected release and circuits, diagnostics, and remediation classes. Feedback is an explicit reviewer statement about a run, observation, finding, severity, or explanation. It carries the reviewer’s message, type, target, and provenance.

Learning may snapshot both when authorized. Neither has authority to modify a release directly. A production document that says “ignore this rule” remains source data; even if it causes an issue, it does not become rulebook authority.

Provenance and local reproducibility

Canonical serialization and content digests detect accidental changes, close the published file set, key caches, and support semantic diffs. They are local consistency mechanisms, not signatures and not proof that a semantic judgment is correct. A release can reproduce which model capture and observation were accepted; evaluating a live model again is a new inference unless the old capture is explicitly replayed.

The runtime preserves dependencies from source blocks and operational context to observations, circuit nodes, witnesses, and findings. A changed source, identity, calendar, extraction profile, or theory can invalidate dependent results. When a complete slice cannot be demonstrated, the safe behavior is full recomputation.

Debug a run from the outside inward

  1. Read report.md and run.json. Confirm agent, release, terminal status, active and blocked circuits, findings, and issue identifiers.
  2. For a stopped run, inspect compatibility.json and coverage.json. Determine which critical type, scope, status, producer, source, or context was missing.
  3. For a suspect observation, inspect longtext.json, source anchors, and model-captures.json. Verify quotation, block, payload, epistemic status, and producer.
  4. For a wrong derivation, inspect circuit-plan.json and semantic-trace.json. Follow the exact nodes and resolved operator versions.
  5. For a rejected or overclaimed result, inspect verifier-results.json. Compare checked properties and diagnostics with the witness and guarantee.
  6. Record the correction at the failing layer. Use feedback for reviewer evidence or preserve the runtime issue for a later learning job.
