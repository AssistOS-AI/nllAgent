Learning with Coding Agents

Learning in nllAgent is not online self-modification. It is a controlled build process in which a Coding Agent turns rulebooks, calibration documents, benchmark evidence, and production issues into reviewable candidate artifacts. The active release remains frozen throughout.

This page is the operational tutorial. Read Architecture of learning first for the candidate-build and manual-publication boundary.

Why learning is a separate workflow

A natural rule rarely specifies every operational detail. “Do not enter another character’s mind” assumes a definition of scene, focalizer, direct mental access, reported speech, and allowed transitions. Reviewer corrections reveal which assumption was wrong: extraction, identity, scope, exception, policy, severity, or explanation. The system needs an agent capable of editing several coordinated artifacts, not merely a prompt that produces another verdict.

That flexibility is dangerous inside production. A document could contain instruction-like text, a reviewer could suggest a local exception, or a model could choose a convenient interpretation. nllAgent therefore gives the Coding Agent write access only to a disposable learning workspace. Production does not import those skills and cannot mutate the published theory.

flowchart TB
  INPUT[Rules + examples + issues] --> STAGE[Coding Agent staging]
  STAGE --> AUDIT{Host audit}
  AUDIT -->|safe| CAND[Candidate ready for manual publication]
  AUDIT -->|unsafe| REJECT[Rejected learning run]

Learning produces a candidate, never a live rule. The Coding Agent may propose coordinated changes. A maintainer later chooses whether to invoke the manual publication command.

Start a learning run

nllagent learn \
  --agent editorial \
  --rules ./rulebook

The command locks the named agent, snapshots all rule Markdown files, selected issues and context, the active release, and the current authoring surface, then creates learning-runs/<learning-id>/workspace/. The configured Coding Agent process runs there with a bounded timeout and explicit final-output schema. The current reference adapter invokes OpenAI Codex, so --codex-bin is the shipped executable override; the learning contract itself is generic.

The learning command has no publication flag. It may create or update candidate packages, but it cannot invoke publishRelease() or change the active pointer.

Inside the staging workspace

The workspace is a disposable copy, not a symlink to the live authoring tree. It contains the learning task, read-only snapshots and context, candidate-editable directories, the explicit result schema, and links to only the five learning skills. Process events, final output, diagnostics, and before/after inventories remain under the learning run for audit.

The Coding Agent receives a concrete contract: working directory, allowed skill names, allowed write roots, output schema, timeout, environment, non-interactive process behavior, and diagnostic locations. Different Coding Agent products may implement that boundary differently. Release semantics do not depend on vendor-specific flags.

The five learning skills form one compilation pipeline

SkillMain questionPrincipal artifacts
nll-scope-projectWhat is the intended use, authority, document population, finding contract, and automation limit?Scope contract, authority map, declared gaps.
nll-compile-theoryWhat is observable in LongTextJS and what must the reusable CircuitJS theory derive?Rule cards, schemas, extraction profiles, circuits, witness and compatibility declarations.
nll-build-benchmarkWhich natural positive, negative, exception, ambiguity, coverage, and long-range cases define the intended behavior?Microcases, suites, expected layers, coverage matrix, counterexamples.
nll-learn-from-issuesWhich layer caused each real failure and what is the smallest general repair?Distilled cases, patches, new limits, regression evidence.
nll-prepare-releaseIs the candidate internally complete and ready for a maintainer to consider publishing?Candidate manifest, public-check results, impact explanation, and known limitations.

Skills guide the Coding Agent but are not trusted evaluators. Their output still passes parsers, schemas, circuit compilation, registry linking, benchmark execution, and host policy. The learning catalog is intentionally separate from repository-maintenance skills and from the narrow production observation and optional CNL-realization skills.

What may be changed

Learning can promote changed regular files only under the agent’s authoring roots: rule cards or authority-derived documentation, observation schemas, extraction profiles, restricted circuits, benchmark cases and suites, proposals, and candidate packages. The runner rejects deletions, symbolic links, writes outside the whitelist, or an absent, unreadable, or schema-invalid final result.

The Coding Agent cannot change runtime source, verifier implementations, operator registries, publication policy, previously published releases, production run history, or the active pointer. When a rule needs a new trusted capability, learning writes a proposal instead of hiding code inside a circuit.

flowchart TB
  EDIT[Editable candidate files] --> DIFF[Before/after inventory]
  DIFF --> POLICY{Whitelist + no delete/symlink}
  POLICY -->|pass| PROMOTE[Promote regular files]
  POLICY -->|fail| REJECT[Reject entire learning job]

Promotion is an all-or-nothing policy decision. A plausible final message cannot excuse a forbidden filesystem change. Unsafe staging output never reaches the live authoring surface.

Walkthrough: from a false positive to a release

Suppose an editorial rule reports the phrase “in fact” inside dialogue even though the guide restricts it only in narration.

  1. Feedback captures the disputed layer. The reviewer attaches a false-positive or scope correction to the run and points to the dialogue passage.
  2. Learning snapshots the case. The issue, source evidence, current circuit, relevant extraction profile, and existing tests enter a new staging workspace.
  3. The failure is distilled. The Coding Agent creates a small natural positive case in narration, a close negative case in dialogue, and—if needed—a reported-speech boundary case. It does not reduce them to preapproved facts.
  4. The correct layer is patched. If discourse mode was extracted correctly, the CircuitJS scope filter changes. If dialogue was misclassified, the extraction profile and expected observation layer change instead. The distinction is visible.
  5. Local candidate tests run. Existing positive cases must remain valid while the new negative case stops producing a finding.
  6. The host audits and promotes. Only allowed candidate files leave staging.
  7. A maintainer publishes explicitly. Observation alignment, circuit compilation, natural suites, and immutable candidate digests must pass. A semantic diff records the affected rule and behavior.
  8. Publication selects the new release. The old run remains unchanged. A new production run under the newly active release demonstrates the repaired behavior.

Publish a selected candidate manually

nllagent release publish \
  --agent editorial \
  --candidate 0.1.0

Only this explicit command enters the release manager. It validates manifests and containment, parses restricted circuits, links operators and verifiers, derives critical observation contracts, confirms producer alignment, snapshots benchmark and candidate bytes, runs all declared suites, and checks that neither snapshot changed during execution.

On success it copies an immutable release containing theory, extraction, compatibility, benchmark snapshot and results, semantic diff, impact map, observation contracts, alignment report, and digests, then updates the active pointer. On failure it produces diagnostics and leaves production unchanged. Benchmarks and publication checks explains the checks and current limitations.

Working with several specialized agents

The runtime supports many named nllAgent workspaces and therefore many independent Coding Agent learning jobs. An editorial agent can evolve focalization and continuity circuits while a compliance agent evolves obligations and deadline benchmarks. Their workspaces, locks, authority, candidates, project knowledge, releases, and active pointers remain separate. The shared runtime contributes only stable DSLs, registries, storage formats, and publication behavior.

This separation is preferable to a single agent with a giant mixed rulebook. It keeps ontology contracts small, benchmark failures attributable, release semantics reviewable, and domain authority explicit. Shared patterns should become reviewed schemas, operators, or templates—not copy-by-conversation between active production theories.

When not to open learning

  • When the missing input is an operational source, calendar, credential, or complete register that can simply be supplied.
  • When a one-off document is outside intended use and the project does not want to support that document family.
  • When feedback is vague and cannot identify an anchor, observation, rule, exception, severity, or expected behavior.
  • When a policy owner has not resolved a genuinely contested rule; the correct output may remain review-required.
  • When the change requires a new trusted operator or verifier; learning should produce a proposal and tests, not bypass the platform boundary.
