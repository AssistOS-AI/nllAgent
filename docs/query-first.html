Query-first CircuitJS implementation

Routine relational rules should be reviewable as typed queries and evidence-aware decisions over one canonical LongTextJS program. They should still compile to ordinary CircuitJS, pass through independent verifiers, and preserve the mathematical operators used by complex circuits.

Status: experimental subset implemented. The loader accepts one direct queryFirstCircuit({...}); the compiler validates and lowers LongTextQuery@1 plus DecisionTable@1; the scheduler executes the generated graph; publication persists query artifacts and benchmarks compare reference and lowered execution. Aggregates, ordered patterns, native indexes, arbitrary semantic schema registries, and compile-time overlap proofs are not implemented.

Query-first is for visible selection and decisions, not hidden callbacks. Real JavaScript algorithms use a direct CircuitJS node and a trusted registered extension. The runnable programmer example shows that path.

One meaning, one publication path. The query layer selects and relates canonical data. It cannot create evidence or emit. Physical indexes never change the query result or its guarantee.

LongTextJS relation map

The query adapter follows the real LongTextProgram shape. It does not invent a plural source catalog or require a database server.

Observation scans have built-in field catalogs for deterministic document structure and the shipped foundation types. Other semantic observation types must declare fields explicitly until schemas move into the trusted registry; a declared path constrains syntax but does not by itself prove domain meaning.

The normalized query is data

This executable normalized value states exactly which observations are selected, which fields are read, and which total order is required. It contains no callback:

{
  "kind": "LongTextQuery",
  "schemaVersion": 1,
  "id": "q:narrative-paragraphs",
  "from": {
    "relation": "observations",
    "as": "p",
    "type": "document.paragraph@1",
    "statuses": ["extracted"]
  },
  "where": {
    "op": "eq",
    "left": { "field": "p.payload.structuralRole" },
    "right": { "literal": "paragraph" }
  },
  "select": {
    "paragraph": { "ref": "p" },
    "text": { "field": "p.payload.text" }
  },
  "orderBy": [
    { "expr": { "field": "p.payload.order" }, "direction": "asc" },
    { "expr": { "field": "p.id" }, "direction": "asc" }
  ]
}

The implemented subset is intentionally small: canonical relation scan, typed three-valued filter, projection, inner join, semi-join, exact coverage-aware anti-join, and total ordering. Scalar operations are eq, neq, gt, gte, lt, lte, in, includes, startsWith, endsWith, and literal Unicode-aware wholeWord; logical operations are and, or, not, and isPresent. Left join, correlated subqueries, grouping, aggregates, distinctness, union, intervals, limits, and patterns are rejected.

What a query produces

A query result is not just an array. Its envelope contains program and query digests, row schema, deterministic rows, coverage evaluation, diagnostics, and counters. Each row contains a stable derived row id, projected values or canonical references, and dependencies on source objects, observations, coverage tokens, registered functions, and assumptions. Projection can hide a field from display but cannot erase its evidence dependency.

Three-valued truth and explicit execution refusal

StateMeaningAllowed consequence
TRUE / MATCHThe typed condition is established and required coverage is satisfied.Construct a candidate and witness, then verify.
FALSE / NO_MATCHThe condition is determinately false.No candidate for this row.
UNKNOWNA material value or completeness fact is unavailable.Produce an undetermined record when material; never coerce to false.
BLOCKEDCompatibility, integrity, capability, budget, or block-circuit unknown policy forbids responsible evaluation.Stop outside the row truth result with a typed error.

The implemented anti-join retains an unmatched left row only when a verified, failure-free closed-world token matches the current source revision, declared scope, channels, type, producer, method, exclusions, and the producer capability supports the accepted statuses. Otherwise it produces an incomplete query state and no negative row. Correlated notExists, domain-specific failure matching, world-aware signatures, and broader subsumption remain deferred.

Evidence-aware decisions

An implemented DecisionTable@1 row contains a stable row id, authority references, typed input query, condition, priority when required, and a plain-data candidate template. The table declares report-undetermined or block-circuit for unknowns and one exact verifier shared by its rows. The compiler constructs a QueryDecisionWitness; the row cannot certify or emit.

Hit policyBehaviorFailure
uniqueAt most one row matches one input.More than one match is decision overlap.
priorityThe unique highest explicit priority or override wins.A tie is a publication or execution error.
collectEvery matching row constructs a candidate in query order, then descending optional priority and stable row id.Forbidden candidate conflicts remain visible.

Do not make everything a table

RuleSimplest correct form
Exact lexical or domain algorithm already existscall → verify → emit with one reviewed policy object.
Many local alternatives share one data domainNamed query plus decision table.
Count or ratio over a complete groupQuery plus registered aggregate and member witness.
Short bounded ordered sequenceOrdered query plus registered pattern operator.
Recursive closure, truth maintenance, complex state, solver, search, or argumentationDirect CircuitJS graph and exact registered algorithm.

Explanation survives lowering

The generated source map connects query and table identities to generated nodes, and scheduler trace entries carry the same logical metadata. QueryResult, DecisionRecord, QueryDecisionWitness, and QueryDecisionCertificate show the selected domain, condition truth, unknowns, dependencies, coverage token, verifier, and publication path. Author line and column mapping plus a dedicated CNL explanation renderer remain future work.

Current practical rule. Learning may emit the implemented subset only when a shared relational decision family is clearer than an exact operator wrapper. Unsupported forms stay direct CircuitJS or exact registered operators. The published editorial demonstration remains direct because its three-node graph is already simpler.

A direct CircuitJS observationBinding() can already apply a short AND-list of local field matchers. Choose it for one relation and no derived rows. Query-first starts where the problem needs lexical aliases, projection, joins, deterministic ordering, evidence-aware decisions, or coverage-sensitive absence. The two forms therefore share a data boundary without pretending that a binding is a general query engine.
