Natural cases define the operational meaning of a theory

Benchmarks that can reject a plausible mistake

An nllAgent benchmark begins with the kind of text production will receive, not with preformalized facts. Each case separately states what LongTextJS should observe and what CircuitJS should conclude, so a failure can be traced to translation, identity, coverage, theory, verification, or reporting.

Why cases remain natural text

If a focalization test starts with JSON saying experiencer=Bob and focalizer=Alice, it proves only that the circuit can compare two values. It does not test whether the system can distinguish direct mental access from a visible inference in prose. Conversely, treating a hundred-page novel as one test makes disagreement almost impossible to localize.

nllAgent uses small natural microcases for precise properties and larger scenarios for composition. A microcase can be a paragraph, short scene, table fragment, or several distant excerpts joined by a context envelope. It preserves the minimum context needed for the rule while retaining source-like language.

One case, several oracles. Natural input exercises the whole pipeline. Structured layers locate the cause of failure; the Markdown expectation keeps the human-facing contract visible.

The executable case folder

benchmark/public/ed001-dialogue-exception/
├── input.md
├── expected.md
├── expected.json
└── case.json
FilePurpose
input.mdThe untrusted natural document fragment given to the same production analyzer used by ordinary runs.
expected.jsonStructured assertions for terminal and compatibility status, observations and payload fields, coverage, finding count and rules, verdicts, severity, guarantees, and evidence quotes.
expected.mdThe reviewer-facing expected report. It keeps explanation and visible limitations part of the contract.
case.jsonRule, family, validation status, report comparison mode, rationale, and optional semantic rubric or transformation lineage.

All four must be regular files in an agent-owned directory. Incomplete folders, symlinks, duplicate case identifiers, or missing expected layers fail the benchmark. A case may additionally carry approved observations, context-envelope metadata, transformation lineage, or fixture context.

A concrete structured expectation

{
  "schemaVersion": 1,
  "observations": [
    {
      "type": "document.paragraph@1",
      "quote": "In fact"
    }
  ],
  "circuit": {
    "status": "reported",
    "findingCount": 1,
    "findingRules": ["ED-001"]
  }
}

This assertion says which source-grounded observation matters and which circuit result must follow. It does not force byte-for-byte report prose unless the case selects exact comparison.

Case families separate neighboring meanings

A positive example alone rewards over-generalization. Each executable rule should have the families relevant to its semantics:

FamilyQuestion it answersExample distinction
Positive and close-negativeDoes the circuit recognize the phenomenon without capturing nearby valid text?Direct mental access versus visible inference.
BoundaryIs an exact threshold or interval edge implemented correctly?Two allowed occurrences versus three prohibited occurrences.
ScopeIs grouping performed over the correct paragraph, scene, actor, version, or jurisdiction?Three uses in one paragraph versus three across a chapter.
ExceptionDoes the approved exception defeat the general rule in the right scope?Weak phrase in narration versus dialogue.
AmbiguityDoes material interpretive uncertainty produce alternatives or review rather than a forced label?Unresolved focalizer or entity identity.
CoverageDoes the circuit know when absence is and is not evidence?Complete official register versus selected emails.
Long-rangeCan locally correct observations compose across distant passages?Object left in chapter 2 and used in chapter 7.
AdversarialDoes source structure remain data under misleading surface forms?Rule-like instructions inside a fenced code block.

Suites organize workflow, not truth

Suite directoryOperational role
publicClear examples visible during theory authoring and ordinary regression checks.
developmentCases used while comparing candidate circuits or extraction profiles.
holdoutCases omitted by convention from a particular synthesis prompt. The folder is not a confidentiality boundary.
scenariosLonger compositions testing identity, time, scope, and distant exceptions.
adversarialInstruction-like source, code fences, Unicode, malformed structure, and shallow-pattern traps.
metamorphicControlled transformations with an invariant or intentionally changed outcome.
mutationsNatural cases aimed at known defect classes; not, by themselves, generated program mutation testing.

The runner discovers every available group independently, and benchmark policy can require named suites, minimum counts, and per-rule families. Independence is a property of source wording, authors, structures, scopes, and failure paths—not merely the directory name.

How one case is evaluated

  1. The runner creates an isolated analysis context with the candidate or selected release and the case’s natural input.
  2. The normal LongTextJS compiler, translation route, compatibility gate, circuit scheduler, verifier, and report renderer execute.
  3. Structured comparison checks the declared observation and circuit layers: status, compatibility, finding count and rule, payload fields, quote, coverage, severity, and guarantee.
  4. The report comparison mode applies: exact normalizes only line endings and trailing whitespace; structured uses layer assertions as the authoritative oracle; semantic additionally invokes a rubric-based evaluator.
  5. The case result records mismatches by layer, backend captures where applicable, duration, and the tested release or candidate identity.
flowchart TB
  RUN[Execute natural case] --> STRUCT[Structured assertions]
  RUN --> SEM[Semantic perspectives]
  STRUCT --> RESULT[Layered case result]
  SEM --> RESULT
  RESULT --> GATE[Suite and publication policy]

Structured truth stays primary. Semantic evaluation can detect a materially changed explanation, but it cannot excuse wrong status, observations, coverage, findings, or guarantees.

Semantic comparison is adversarial, not similarity scoring

When a case selects semantic comparison, the evaluator receives the expected layers, expected report, actual report, and a versioned rubric. One perspective tests material equivalence; another tries to construct a counterexample by identifying changed rules, scope, evidence, coverage, limitations, or guarantee. Disagreement fails or routes to review according to policy.

The evaluator uses the same backend-neutral model boundary as translation. Configured AchillesAgentLib is preferred and translation-class evaluation uses Spark when exposed. A Coding Agent adapter can return the same evaluation schema. The evaluator’s decision is model evidence with captures, not a mechanical proof.

Author a useful new case

  1. Start from a real rule, issue, or calibration passage and identify the one property the case must distinguish.
  2. Keep natural wording and enough context for the decision. Remove irrelevant sentences only if the expected observation and verdict remain stable.
  3. Create the closest plausible opposite: change modality, negation, scope, identity, threshold, exception, or coverage rather than writing an unrelated negative.
  4. Write expected LongTextJS observations independently of the finding. Include type, quote, payload, polarity, modality, identity, or coverage fields that matter.
  5. Write expected CircuitJS behavior: finding, no finding, not-applicable, ambiguity, stopped state, or review requirement.
  6. Give the case a validation status such as mechanically derived, model-agreed under a recorded protocol, human-confirmed, draft, or contested.
  7. Run the complete suite and confirm the new case rejects the intended defect without rewriting older oracles.

From candidate to immutable release

nllagent benchmark --agent editorial --json
nllagent release publish --agent editorial --candidate 0.1.0

The manual publication command applies checks in dependency order. Later utility cannot compensate for an earlier safety failure:

  1. Validate candidate and benchmark containment, regular files, manifests, schemas, restricted module form, and canonical artifacts.
  2. Compile every circuit, link exact operator and verifier versions, enforce verification dominance, and derive observation contracts.
  3. Reject critical circuit inputs without a structural producer, extraction profile, or approved adapter.
  4. Snapshot candidate and benchmark bytes, execute every declared natural suite, and apply case-count and per-rule family policy.
  5. Confirm candidate and benchmark bytes did not change during execution.
  6. Compute the semantic circuit diff and impact map against lineage.
  7. Copy the exact tested snapshots into a temporary release, verify the copies and digests, persist results and alignment artifacts, and atomically publish the immutable version.
  8. Update the active pointer only after the immutable release has been loaded and verified successfully.

What publication checks currently prove

The implemented local gate proves the static CircuitJS and registry checks it records, critical observation-producer alignment, structured results for every suite it executes, declared benchmark-policy coverage, candidate and benchmark snapshot stability, local digests, semantic diff, and impact mapping. The included editorial-demo currently exercises ten public and adversarial cases across two lexical rules, including positive, clean negative, whole-word, exact threshold, paragraph scope, dialogue exceptions, code-fence scope, and instruction-like source text.

Do not overread the checks. The repository does not yet generate mutated CircuitJS or LongTextJS programs and calculate a mutation score. It also does not yet run differential implementations, shadow or canary traffic, or a complete precision, recall, latency, cost, review-time, and complexity evaluation program. A natural case stored under benchmark/mutations/ is useful, but is not equivalent to generated mutation execution. These limits remain explicit in serious issues.
