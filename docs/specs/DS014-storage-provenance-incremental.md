# Introduction

Codex succeeds here only when it receives the relevant theory, exact executable vocabulary, and a narrow writable
workspace. A large catalog of vague skills fragments the architecture and encourages local patches. nllAgent therefore
has three product skills, each backed by detailed theory references and native context-checking code.

# Core Content

## The three skills

`nll-train-agent` owns complete theory compilation. Its SKILL.md explains the language family and mandatory lifecycle,
then links focused references for rule analysis, ontology boundaries, circuit and method design, materialization demand,
assurance, benchmarks, and build assembly. It may modify only the candidate workspace.

`nll-analyze-task` owns source-to-LongTextJS materialization for one selected agent build. It explains the ground-only
contract, claims versus truth, identity and alternatives, scope/coverage, exact Unicode anchors, and multi-file document
composition. It may modify only the task's generation workspace and final LongText folder. It cannot add ontology
constructors, circuits, or findings.

`nll-review-and-repair` owns independent semantic review and layer-correct repair of a candidate. It links authority
traceability, ontology/LongText/Circuit category checks, benchmark and mutation review, and diagnostic routing. It does
not modify a promoted build or another agent.

These are nll product skills. Imported GAMP, article, or platform skills remain untouched and are not installed into a
runtime Codex workspace.

## AgentAuthoringContext

The host compiles a typed opaque `AgentAuthoringContext` from one AgentProject and one exact build. It contains:

- purpose: `TRAIN`, `ANALYZE`, or `REVIEW`;
- agent and build identity plus a content digest;
- all selected ontology identities and public constructors;
- root and nested circuits, methods, effects, decision tables, and providers;
- the one MaterializationProfile and recursively derived SemanticDemand;
- exact concept, role, capability, operation, evidence-policy, and coverage-scope demands;
- allowed SDK module imports and registered primitive providers;
- theory, test, and benchmark resources relevant to the role;
- native commands that validate the result.

The durable context is an executable `.mjs` module plus an equivalent Markdown view. Skill-owned `check-context.mjs`
loads the module and rejects a wrong purpose, missing build, ambiguous profile, missing SDK provider, or cross-agent
identity. The context is generated by code; Codex does not infer it from directory names.

Training has three context stages. A new agent receives a typed bootstrap TRAIN context derived from core ontology, SDK,
and copied theory. A candidate ready for criticism receives a REVIEW context compiled from its actual modules. A
promoted build receives an ANALYZE context that a future task can use without reading other agents.

## Environment and task isolation

The persistent environment is:

```text
data-root/
  agents/<agent-id>/
    builds/<immutable-build-id>/
    current/agent.mjs
    training-runs/<run-id>/
  tasks/<task-id>/
    input/
    pin/
    generation/
    longtext/
    output/
```

A task pin records the exact agent ID, build ID, build digest, context digest, and source digest in `.mjs`. Analysis copies
only that build into its Codex sandbox. Another agent's ontology or circuit registry is not discoverable there. A task
cannot follow a later `current` pointer change.

Generated modules are treated as untrusted. The host rejects symlinks, disallowed extensions, path escape, unexpected
imports, unrecognized semantic values, source mismatch, and writes outside the owned subtree. Validation and execution
occur in child processes. The deterministic runtime gets no Codex capability.

## Diagnostics and handoff

Diagnostics carry a stable code, file/location, semantic subject, expected/received values, authority or source span,
trace slice, and owner. Ontology errors return to training ontology work; absence/coverage and observation errors return
to materialization; method and composition drift return to planning/circuit work; proof or symbolic gaps return to
assurance; oracle conflict requires independent review.

Handoff is repository evidence: changed files, checks run, reports, unresolved diagnostics, and the next role. A prose
claim that work “looks correct” does not pass a gate.

## Multiple agents in one environment

Agent identity namespaces builds, training runs, contexts, tasks, provider selections, and caches. Content-addressed
reuse across agents is permitted only for immutable values whose complete dependency identity is equal; it never
imports another agent's semantic authority. The CLI always requires or resolves a single selected agent before context
compilation.

# Decisions & Questions

### Question #1: Why only three nll skills?

Response: They match the only three authority boundaries: compile theory, materialize one source, and independently
review/repair. Detailed theory lives in linked references, avoiding both a monolithic prompt and dozens of vague roles.

### Question #2: May the analysis skill read CircuitJS source?

Response: It receives an exact public circuit/demand description and selected build context. It may inspect selected
public modules when necessary, but cannot edit them or access other agents.

### Question #3: Can Codex call arbitrary external models from generated code?

Response: No. Codex is the coding mechanism used by the host. Accepted deterministic circuits have no Coding Agent or
direct model-call capability.

### Question #4: Why keep both `.mjs` and Markdown context?

Response: The module is machine-verifiable and reimportable; Markdown is readable by the coding role and reviewers.
Their digest and content projection are checked together.

### Question #5: What happens if an analysis needs a concept absent from the selected ontology?

Response: LongTextJS records an ontology gap and the analysis is blocked locally. It does not modify the agent. The user
may start a separate retraining operation.
