A practical mental model before the language reference

Circuits, without the mystery

This page explains CircuitJS as ordinary data processing. If you can follow a spreadsheet filter and a short JavaScript function, you can follow the complete example. We will see what data exists, how a circuit asks for it, what happens when there are zero or many records, why graph loops are rejected, and where real JavaScript algorithms belong.

Scope. This is the first programmer-oriented explanation, not the complete field or primitive reference. It uses the implemented Markdown compiler, direct CircuitJS graph, scheduler, and trusted runtime-extension API. The deeper pages are linked exactly where their extra detail becomes useful.

Think of a labelled warehouse and an assembly line

LongTextJS is the labelled warehouse for one document revision. It stores the source, paragraphs, anchors, observations, scopes, coverage, and gaps. CircuitJS is an assembly line installed next to that warehouse. Its observation binding asks for one labelled subset of records; each node receives a value, performs one named operation, and hands a new value to the next node.

flowchart LR
  S["Markdown source"] --> L["LongTextJS records"] --> P["observation binding"] --> O["operator"] --> V["verifier"] --> E["CNL output"]

Nothing happens inside an arrow. The arrow only transfers an immutable value. The box names who is allowed to transform or check it.

How the system knows what to extract

It does not guess. During compilation it walks backward from each declared output. In this example the output reads findings; that reads verified; verification reads candidates; candidate construction reads the paragraphs binding. The resulting observation contract says exactly:

paragraphs:
  type       document.paragraph@1
  status     extracted
  cardinality many
  coverage   closed-world
  critical   true

Built-in Markdown structure is always compiled. If an output-reachable observation binding asks for a semantic type such as narrative.object-event@1, publication must link that type to an approved producer and the current run asks that producer for neutral events. A dead node or unused binding is rejected, so it cannot secretly trigger work. The complete producer and compatibility check is the observation contract.

An observation binding is a small, concrete selector

The current scheduler evaluates a direct binding in four steps: exact nominal type, accepted status, an optional AND-list of safe local field matchers, then cardinality. Source order is preserved.

CardinalityAccepted countIf the count is wrong
manyzero or moreThe node receives an array, including [].
oneexactly oneport-cardinality-failed
optionalzero or oneMore than one is ambiguous and fails.
at-least-oneone or moreZero fails instead of pretending the domain is empty.

Local matchers support strict eq/neq, finite-number comparisons, includes, in, startsWith, and exists. They are useful for a field such as payload.structuralRole; they never use JavaScript coercion. Joins, grouping, reusable expressions, order-sensitive logic, and coverage-aware absence belong in Query-First or a registered operator. A binding is deliberately not a second query language.

Read the actual CircuitJS dataflow

export default circuit({
  kind: 'CircuitJS',
  id: 'example.paragraph-length',
  version: '1.0.0',
  inputs: {
    paragraphs: observationBinding({
      type: 'document.paragraph@1',
      cardinality: 'many',
      statuses: ['extracted'],
      coverage: 'closed-world',
      critical: true,
      where: [{
        path: 'payload.structuralRole',
        operator: 'eq',
        value: 'paragraph'
      }]
    })
  },
  nodes: [{
    id: 'candidates',
    primitive: 'call',
    operator: 'example.paragraph-length@1',
    inputs: { paragraphs: binding('paragraphs'), maximumWords: 12 }
  }, {
    id: 'verified',
    primitive: 'verify',
    verifier: 'example.paragraph-length@1',
    inputs: { candidates: node('candidates') }
  }, {
    id: 'findings',
    primitive: 'emit',
    inputs: { verified: node('verified') }
  }],
  outputs: { findings: node('findings') }
});

This is JavaScript-friendly author syntax, but binding() and node() only construct data references. Before production, the file becomes one plain-data graph. At runtime:

  1. observationBinding() selects ordinary paragraphs; binding('paragraphs') resolves to that immutable array. Legacy port('paragraphs') creates the same canonical reference.
  2. candidates receives that array and the number 12. It returns one candidate for the long paragraph.
  3. node('candidates') resolves to that complete candidate array. The verifier recounts the canonical paragraph and checks the source anchor.
  4. emit keeps only records whose verifier status is accept. The result enters the CNL audit assembler.

What happens with many records

A many binding is one ordered array. The operator decides whether to map each record independently, join records, group them, maintain state, search, or return no result. In this example it uses flatMap: every paragraph yields zero or one candidate, so ten long paragraphs yield ten candidates in input order. The verifier receives all ten and returns ten independent replay records.

When the intended operation is relational rather than algorithmic, the experimental query-first profile makes the filtering visible instead of hiding it in a function:

from: {
  relation: 'observations',
  as: 'p',
  type: 'document.paragraph@1',
  statuses: ['extracted']
},
where: {
  op: 'eq',
  left: { field: 'p.payload.structuralRole' },
  right: { literal: 'paragraph' }
},
orderBy: [
  { expr: { field: 'p.payload.order' }, direction: 'asc' },
  { expr: { field: 'p.id' }, direction: 'asc' }
]

Use query-first for supported scans, filters, joins, exceptions, and decision rows. Use a direct graph and registered operator when the processing is a real algorithm. A query row cannot run a JavaScript callback.

Why the graph does not accidentally loop forever

The compiler builds dependencies from every node() reference and topologically sorts them. If A depends on B and B depends on A, compilation stops with circuit-cycle. The scheduler never reaches that graph. It currently executes the finite sorted list once.

Algorithms that genuinely iterate are enclosed in one explicit, budgeted node. A positive rule closure uses a fixpoint operator with a finite domain and deduplication. A timeline uses maintain. A path finder uses search with state and frontier limits. Their internal loops are real JavaScript or solver work, but their termination policy, result, witness, and failure remain one visible node contract.

Where real JavaScript processing lives

The repository's runnable example places this function in a trusted runtime extension:

function paragraphCandidates({ paragraphs = [], maximumWords = 12 }, context) {
  return paragraphs.flatMap((paragraph) => {
    const count = words(paragraph.payload.text).length;
    if (count <= maximumWords) return [];
    return [{
      kind: 'FindingCandidate',
      rule: 'EXAMPLE-PARAGRAPH-LENGTH-001',
      subject: paragraph.id,
      mainAnchor: context.program.anchors[paragraph.anchors[0]],
      supportAnchors: paragraph.anchors.slice(1),
      sourceRuleReferences: context.circuit.sourceRuleReferences,
      witness: { observationId: paragraph.id, count, maximumWords }
    }]; // The complete example also supplies severity, remediation, and limitations.
  });
}

The module exports NllRuntimeExtension metadata, structured input/output schemas, the operator, and a separate verifier. A host application loads it explicitly:

const registries = createStandardRegistries();
await loadAndInstallRuntimeExtension(
  registries,
  './examples/runtime-extension/paragraph-length.extension.mjs'
);

const circuit = compileCircuit(authorValue, registries);
const result = await executeCircuit(circuit, longTextProgram, registries);

Run the complete repository example with:

node examples/runtime-extension/run.mjs

Its output shows the extension digest, compiler order, verified finding, and per-node trace. Extension inputs and context are frozen plain-data copies. Compilation rejects wrong fields and literals, runtime rejects values that violate the schemas, and non-plain output is rejected. The digest enters cache identity, and a published release that calls the extension must lock the same id and digest.

Trust boundary. The extension is normal JavaScript running in the host process. It is for reviewed application code, not user documents or learned circuits. The standard CLI does not accept an extension path. The host uses the ESM library API because loading the module grants code authority.

What the result means

For the example input, the operator counts 17 words in the second paragraph. The verifier independently obtains the observation from LongTextJS, recounts 17, checks 17 > 12, and confirms the anchor. The emitted finding records mechanically-certified, the witness, certificate, source digest, remediation, and the limitation that this example defines a word by Unicode whitespace.

For a combined run that also triggers foundation logic and exact arithmetic, execute node examples/advanced-circuit/run.mjs and follow the advanced circuit tutorial. It renders the actual CNL/Audit-1 report instead of stopping at node output.

That is the complete pattern: LongTextJS supplies addressed facts about one source; CircuitJS fixes dataflow and policy; executable operators do the hard work; verifiers bound the claim; CNL presents the accepted result.
